## [1.2.2] - Unreleased

### Added

- **Telegram notifications reach several chats, and land in the right group topic** — Every chat-id setting now takes a comma-separated list: the management chat `TELEGRAM_CHAT_ID` and the error-log chat `TELEGRAM_LOG_CHAT_ID` alike, not just the signals channel `TELEGRAM_CHAT_CHANNEL_ID` that already did. None of them is special-cased any more, since all three resolve through one parser (`notification_service.parse_chat_targets`), which accepts both a raw string and the pre-split list `TelegramSettings.parse_channel_ids` produces. On top of the list, an entry may address a single **topic** of a supergroup that has the Topics feature enabled by suffixing the topic id: `-1002173777783_924584`. Such an entry is split into the chat and its `message_thread_id` — the Bot API field for "the target message thread (topic) of a forum" — which is the only way a bot can post into a specific topic instead of *General*; both numbers are the ones in the topic's own link (`t.me/c/2173777783/924584`). The field is sent **only** for topic entries, since Telegram answers `400 Bad Request: message thread not found` when it is passed for a chat without that thread. Only numeric chat ids may carry the suffix, so a username that itself contains underscores (`@my_group_2`) is never mistaken for one; plain ids, user ids and `@username` handles are unchanged. Each chat gets its own Bot API call, so a chat that rejects the send (bot kicked, topic deleted) is logged without stopping delivery to the rest — `send_message()` still reports `False` when any of them failed. Blank entries are skipped and duplicates collapse, so a stray comma or a chat listed twice never double-posts, and `WorkerContext`'s `[settings_dict.get("telegram_chat_id")]` fallback no longer turns a missing key into a literal `"None"` chat.
- Every close notification now reports what the close **booked**. A partial or full close is the moment a trade realizes money, but the Telegram message for it reported prices, volumes and tickets and never the result — so the one question an operator actually has on seeing an exit ("did that make money?") could not be answered from the chat at all, only by opening the terminal or the exchange. A `PnL:` line now sits on every close message, whatever triggered it: `Order Filled` for an exit action (`TP1`/`TP2`/`SL`/`R_SL`/`FLAT`), `Force Closed`, `Admin FLAT Closed`, `Terminal Close`, `Exchange Close`, `Position Reconciled`, and the emergency close reported by `Unprotected Position`. Entries are deliberately untouched — they have booked nothing yet, and a `0.00` there would read as a break-even trade.

  The figure is carried on a new `TradeResult.profit` and rendered through a single shared `pnl_line()`, so all of them share one format (signed, 2dp, 📈/📉) rather than each market inventing its own. `Exchange Close` — the one message that already printed a realized figure — was moved onto the same line so it stops being the odd one out.

  Each path reports the most authoritative number available to it, which differs by market because the brokers differ. **FOREX** reads it from MT5: `order_send` returns no money figure at all, so a worker-placed close looks up the deal it produced (`OrderSendResult.deal` → `history_deals_get`) and reports it net of commission/swap/fee — MT5 has already done the contract-size and account-currency conversion the worker cannot do itself from lots and prices. A terminal-side close gets it free from the deal `close_detector` had already read, and the reconciler (which never saw the close, only a ticket) sums the position's whole deal history and labels it `PnL (position total)`. **CRYPTO** computes `(exit − entry) × qty` signed by side: that is not an approximation of the exchange's number but the definition it uses for a linear USDⓈ-margined contract, so a worker-placed close reports the same figure Binance's own `realizedPnl` would — without a second REST round-trip on the order path, and consistently with the exchange-side closes the user-data stream delivers (both exclude commission and funding). Only the crypto reconciler estimates, measuring the DB row against the same approximate close price the message already shows, labelled `PnL (est.)`.

  Two rules keep the line honest. An amount that could not be read renders `n/a` and is never dropped — silence reads as break-even, and `0.00` would be a fabrication, so `0.00` is reserved for a close that genuinely broke even. And where one logical exit fans out into several broker closes (a symbol held as multiple tickets, a netted FLAT), the reported figure is their **sum**, unlike the `price`/`volume` on the same message which describe the last fill alone. Reading the PnL is best-effort throughout: the close has already succeeded by the time it is fetched, so a terminal that cannot answer costs the line, never the trade.

### Fixed

- FOREX: a symbol with **no live quote** no longer produces a malformed order. `MT5Gateway.get_tick` tested only `if not t`, but `symbol_info_tick` returns a **namedtuple** — truthy even when every field is zero, which is exactly what the terminal reports for a symbol it holds no price for (freshly added to Market Watch, or outside its trading session). That zeroed tick was wrapped as a valid `Tick(bid=0.0, ask=0.0)` and went on to price a live entry: `LotSizer` measured the SL distance against a `0.0` entry (172,686 points for a 1726.86 stop, flooring the lot to `volume_min` so the resulting size *looked* plausible), and `StopValidator` computed `max_sl = bid - stop_dist = 0.0`, judged the signal's stop "too close", and emitted `round(0.0 - point, digits) = -0.01` — while leaving TP untouched, since `tp <= 0.0` is false. The broker rejected the resulting order with retcode `10016 TRADE_RETCODE_INVALID_STOPS`, whose "Invalid stops" message points at the stop distance rather than the missing quote that actually caused it. Guarded at every layer that can observe the problem, so no single missed check re-opens it: `MT5Gateway.get_tick` now treats a non-positive bid/ask as "no data" and returns `None`, so entries **and** closes fail fast (and `ForexSignalProcessor._best_effort_price` no longer reports a `0.0` mid); `StopValidator.validate_stops` refuses to anchor on an unusable tick and never returns a non-positive stop, falling back to the signal's own level so the broker judges it on its own terms rather than being handed a fabricated one; and `ForexExecutor.open_position` rejects a non-positive entry price whatever the gateway returned. Note the behavioural consequence: a signal arriving while its symbol has no quote is now **dropped** with `No tick / market data unavailable` naming the real cause, rather than executed wrongly.
- FOREX: `SymbolResolver` now waits for the terminal's first real quote (2 s cap, 0.1 s poll) after `symbol_select` adds a symbol to Market Watch, instead of returning the instant the call is made. `symbol_select` only *asks* the terminal to subscribe — the first tick lands a moment later — so the **very first signal for a symbol** raced it and read exactly the zeroed tick described above. Resolution still succeeds when the wait times out (a symbol outside its trading session never quotes), leaving the caller's own tick check to fail the trade cleanly instead of blocking the signal thread indefinitely.

## [1.2.1] - 2026-08-10

### Added

- FOREX: `FOREX_ALLOW_MULTI_STRATEGY_PER_SYMBOL` (bool, default `false`) env var — a FOREX-only toggle for holding **several strategies' positions on the same symbol at once**. Until now `SignalHandler._handle_entry` rejected any `LONG`/`SHORT` on a symbol another strategy already held ("netting conflict"), which is the right default for a CEX but needlessly restrictive on FOREX: there every strategy trades under its own magic number (`STRATEGY_MAGIC_MAP`), so the platform keeps each position's ticket, SL/TP and closes fully isolated. With the toggle on, the entry is allowed through and the two strategies run in parallel on that symbol; with it off (default) the previous rejection is unchanged. Requires a **hedging** account — on a netting account the broker merges both strategies into a single net position and the isolation is lost. The rule this does **not** relax is one open order per `(strategy, symbol)`: a strategy re-entering or scaling into its own symbol still force-closes and replaces its existing position, enforced as before by the stale-cleanup step and the `uidx_positions_one_active_per_strategy_symbol` unique index.
- The multi-strategy toggle is now resolved **per market** by `ExecutionConfig.from_dict` (`FOREX_ALLOW_MULTI_STRATEGY_PER_SYMBOL` for a FOREX worker, `CRYPTO_ALLOW_MULTI_STRATEGY_PER_SYMBOL` for a CRYPTO one — neither market reads the other's var) and reaches `SignalHandler` through the new `BaseMarketStrategy.allows_multi_strategy_per_symbol` capability, which defaults to `False`. **Only `ForexMarket` reports it.** `CryptoMarket` deliberately does not, so a CRYPTO worker keeps rejecting the entry regardless of its config flag: `CryptoExecutor.get_open_positions` ignores the `strategy` argument (a CEX has no magic-number equivalent) and `cancel_all_orders` is symbol-scoped, so letting a second strategy in would make its stale-cleanup close the first strategy's position and wipe its resting SL/TP. `CRYPTO_ALLOW_MULTI_STRATEGY_PER_SYMBOL` keeps its previous meaning — it relaxes `CryptoExecutor._netting_conflict`, which sits behind the handler guard.
- FOREX: `ForexSignalProcessor._warn_if_multi_strategy_needs_hedging` — a connect-time check that escalates (log + Telegram) when the toggle is on but `account_info().margin_mode` is not `RETAIL_HEDGING`. Per-magic isolation only exists on a hedging account; a netting account merges both strategies into one position, leaving the second strategy owning nothing while every one of its exits fails with "No open position" and the merged volume runs on unmanaged. Warn-only (the worker still trades) since a mid-migration deployment shouldn't be blocked, and silent when the platform does not report a margin mode.
- FOREX: `Settings` now rejects a `STRATEGY_MAGIC_MAP` containing **duplicate magic numbers** when the toggle is on. The magic is the only thing separating two strategies that share a symbol, so a duplicate would silently make them see — and force-close, on the next entry — each other's positions. Unchanged (and unvalidated) when the toggle is off, so existing deployments are unaffected.
- The FOREX startup banner shows `FOREX_ALLOW_MULTI_STRATEGY_PER_SYMBOL: ENABLED` when the toggle is on (omitted when off, so the riskier mode is the one that stands out).
- `WorkerConnectedAckSchema` (`worker/schemas/inbox_schema.py`) now carries **all** of a worker's connect-time config in one payload: `strategy_magic_map: Optional[dict[str, int]]` (the per-strategy MT5 magic-number map) and `retry_signals: list[SignalSchema]` (the recent-signal replay). The broker now **owns** the magic map and pushes it here instead of each worker hardcoding `STRATEGY_MAGIC_MAP` in its `.env`. Applied by the new `BaseSignalProcessor._apply_worker_connected_ack`, which runs the sections **in order — magic map first, replay second**: a replayed FOREX entry is routed by its strategy's magic, so replaying first would make the unknown-strategy guard reject every signal whose magic hadn't landed yet. Ordering alone is not sufficient, though — a section the broker **omitted**, or one the salvage pass dropped, is skipped in order and leaves the worker on whatever it had before (on a first connect: nothing, now that `STRATEGY_MAGIC_MAP` ships empty). The replay is therefore also **gated** on the config it depends on: the new market hook `_replay_blocked_reason()` is consulted after every section has been applied, and FOREX overrides it to skip the whole batch with a single `ERROR` naming the root cause when the worker holds no `strategy_magic_map`. The outcome is the same either way (none of those signals can be routed), but the operator gets one actionable line instead of N per-signal "unknown strategy" rejections that each name a symptom. The base returns `None` (nothing blocks), so CRYPTO — which has no magic concept — replays as before. `_apply_strategy_magic_map` filters the received map to **only** the strategies this worker actually subscribes to (its `NATS_SUBJECTS` minus the control subjects — entries for any other strategy are ignored with a warning), stores it into the live settings under `strategy_magic_map` exactly where the old `.env` value sat (so `PositionCDC` reads it unchanged), and propagates it to the already-built executor via the new market hook `_set_executor_magic_map`. FOREX overrides that hook to call `ForexExecutor.set_strategy_magic_map`, refreshing magic resolution (`_magic_for`) and `owned_magics()`; CRYPTO no-ops (no magic concept — its CDC reads the map from settings). Omitting `strategy_magic_map` (or sending `null`) leaves the worker's current map **untouched**, so a reconnect ACK never wipes the magics it is already trading under; an explicit `{}` clears them. The `STRATEGY_MAGIC_MAP` env var is kept only as an offline/legacy fallback default (empty by default) and is now removed from `.env.example`; a broker push always replaces it. `examples/nats/system.worker_connected_ack.json` shows both sections.
- `ADMIN` `BLOCK_SIGNAL` / `ALLOW_SIGNAL` actions (private subject only) to suspend/resume the worker's execution of incoming SIGNALs. Both are account-scoped, so they are accepted **only** on the worker's private `ADMIN.<market>.<gateway>.<account_id>` subject (the same action on the public `ADMIN` subject is ignored); the payload (`PrivateAdminSignalControlSchema`) requires `market`/`gateway`/`account_id`, re-validated against the worker's identity before the toggle applies. While blocked, every incoming SIGNAL is skipped at the single `_process_signal` funnel — covering both live signals and `RETRY_SIGNALS` replays — while open positions are untouched and can still be closed via an `ADMIN` `FLAT`. A real state change logs and sends a `🛑 Signals Blocked` / `✅ Signals Allowed` notification (repeating the current state is a no-op). The `_signals_blocked` flag is in-memory only, so a worker restart resets it to allowed. New `AdminActionEnum` members `BLOCK_SIGNAL`/`ALLOW_SIGNAL`, a `PrivateAdminSchema` base (shared required composite identity) that `PrivateAdminFlatSchema` and `PrivateAdminSignalControlSchema` extend, presenter methods `signals_blocked`/`signals_allowed`, and example payloads `examples/nats/admin.block_signal.json` / `admin.allow_signal.json`.
- FOREX: `ForexReconcileJob` (`worker/gateways/forex/reconcile_job.py`) — the missed-close durability backstop the FOREX path was missing, so the broker↔DB reconciler now runs for **both** markets. `MT5EventJob` only reports closes the *terminal* initiated (it deliberately skips `DEAL_REASON_EXPERT`, our own `order_send`, to avoid double-firing), which left a real gap: a **TP1 partial close whose volume equalled the whole position** — routine when the entry was already at the broker's minimum lot (e.g. `0.01`, as equity-based auto-sizing often yields) — flattens the position on the broker while the DB row stays `TP1` forever, and the next entry for that strategy is then rejected as "still open". The new daemon thread (`forex-reconcile`, 60 s poll) diffs `ForexExecutor.get_all_open_positions()` against the DB's `OPENED`/`TP1` rows and, once a row matches no live position on **two consecutive scans**, hands it to `ForexSignalProcessor._on_missed_close`: the row is marked `TERMINAL_CLOSED` with a best-effort mid price (`gateway.get_tick`), an author-`terminal` `position_logs` entry, and a comment flagging it as reconciled. `PositionCDC` publishes the status downstream as usual and a `Position Reconciled — Closed on Broker` operator notification is sent. Matching is by ticket (`ref_id` / `ref_source_id`, `int`↔`str` normalised) **or** the row's `(resolved symbol, magic)` slot, so a broker that re-tickets a position after a partial close is never mistaken for a closed one, while another strategy's position on the same symbol never shields a stale row (magic isolation). Scans are skipped over the weekend-closed window and whenever MT5 is disconnected — including a re-check before an empty position list is trusted — because `positions_get() → None` is mapped to `[]` and must never be read as a flat account.
- `BasePositionReconcileJob` (`worker/gateways/reconcile_job.py`) — the market-agnostic reconciler skeleton now shared by FOREX and CRYPTO (Template Method, mirroring `BaseSignalProcessor`). It owns the poll loop, the two-scan confirmation, both reconcile directions (missed closes and — when a `manual_handler` is wired — untracked live positions), and the safety rules: a failed/unavailable position fetch skips the whole scan with both suspect sets untouched, and a row whose match keys cannot be computed (symbol resolution failed, magic unknown) is treated as **live** rather than closed on unverifiable information. Each market supplies only how a live position correlates with a DB row (`_live_keys` / `_db_keys` / `_live_id`), the same variation point `BaseSignalProcessor._flat_match_key` / `_flat_db_match_keys` solves for ADMIN FLAT.

### Changed

- **Breaking (broker payload): `RETRY_SIGNALS` and `STRATEGY_MAGIC_MAP` are removed as standalone SYSTEM actions** — both are now sections inside the single `WORKER_CONNECTED_ACK` reply (`retry_signals` / `strategy_magic_map`), together with a third, `crypto_leverage_init`. `SystemRetrySignalsSchema` and `SystemStrategyMagicMapSchema` are gone. Config now reaches a worker on **two paths, split by *when* the config exists**: connect-time config rides in the ACK (the reply inbox delivers exactly one message), while a setting changed *after* the handshake is broadcast as a standalone action on the shared `SYSTEM` subject, which the worker stays subscribed to for its whole lifetime. `CRYPTO_LEVERAGE_INIT` deliberately **keeps** its standalone action for that runtime path — an admin editing an account's leverage cap has no handshake to attach to — so `_handle_system_message` and the `_handle_system_action` hook stay as the runtime half of the flow. Its payload is now shared by both paths as `CryptoLeverageInitSchema`: nested under `crypto_leverage_init` in the ACK, and flattened into `SystemCryptoLeverageInitSchema` for the broadcast. A market that owns an ACK section implements the new `_apply_market_init(ack)` hook; `CryptoSignalProcessor` overrides it and funnels both deliveries through one `_leverage_init_from` → `_run_leverage_init` path, logging `via ACK` / `via SYSTEM` so an operator can tell a connect-time init from a runtime change. Sections are applied config-first, replay-last, so a replayed CRYPTO entry is sized against the leverage it was meant to trade at. A `CRYPTO_LEVERAGE_INIT` sent as a *reply* to the handshake is no longer accepted — on connect it belongs in the ACK section, at runtime on the broadcast subject. A broker still publishing the old standalone actions now fails envelope validation and is ignored. **Why:** `nc.request` opens a temporary reply inbox, resolves on the **first** message delivered to it, and unsubscribes immediately — so a broker that answered one `WORKER_CONNECTED` with three publishes to that inbox had the other two silently discarded *by the nats-py client*, below the worker's message handler. Nothing was logged on either side (the broker's fire-and-forget `publish` reports success regardless), and which message survived was decided purely by the broker's send order: in practice `STRATEGY_MAGIC_MAP` won, so `RETRY_SIGNALS` and `WORKER_CONNECTED_ACK` never reached the worker at all. Carrying every section in the one reply the request/reply contract actually delivers makes the loss impossible rather than merely unlikely. Merging the sections would normally make one malformed entry able to take the whole ACK down, so `WorkerConnectedAckSchema._salvage_sections` validates each section — and each entry within it — **independently**: a bad signal is dropped without costing the rest of the batch or the magic map, and a bad magic costs only that strategy. Each discarded entry is logged at `ERROR` with its reason. Two deliberate asymmetries: if *every* magic-map entry is unparseable the section is skipped rather than stored as `{}` (an empty map is the broker's explicit "clear my magics" instruction, and a parse failure must not be mistaken for one), and a broken **envelope** still drops the ACK wholesale since it addresses nobody.
- The raw `WORKER_CONNECTED` request and reply are now both logged at `DEBUG` (`WORKER_CONNECTED request payload: {…}` / `WORKER_CONNECTED reply payload: {…}`), the request right before `publisher.request` sends it and the reply before anything is parsed. Neither direction passes through `NATSSubscriber.listen`'s "Received NATS message" DEBUG line the way a subscribed message does — a request rides `publisher.request` and a reply lands on its private inbox — so the exact bytes sent and received were invisible on both sides, which is the one thing you need when a section silently fails to apply. Logging the reply *before* `json.loads` also means a payload that doesn't parse at all leaves more than a bare exception. Enable with `LOG_LEVEL=DEBUG`; the `INFO` summary lines (`Announced WORKER_CONNECTED account_id=…` / `handshake complete | magics=… leverage=… replay=…`) are unchanged.
- `examples/nats/system.retry_signals.json` and `examples/nats/system.strategy_magic_map.json` are removed; `system.worker_connected_ack.json` now shows both sections in one payload, and `subjects.md` documents the one-reply-per-request rule. The README's **SYSTEM Subject** section is rewritten around the same two-path split (a table contrasting connect-time ACK sections with runtime broadcasts, the one-reply-per-request rule spelled out as the reason, a per-field `WORKER_CONNECTED_ACK` payload table covering present/omitted behaviour, and a fault table showing exactly what each kind of malformed section costs), and the **Per-symbol leverage initialisation** section now names both triggers instead of only the reply.
- `SystemWorkerConnectedSchema` / `SystemWorkerConnectedAckSchema` / `SystemWorkerConnectedErrorSchema` moved out of `worker/schemas/system_schema.py` into a new `worker/schemas/inbox_schema.py`, renamed to `WorkerConnectedSchema` / `WorkerConnectedAckSchema` / `WorkerConnectedErrorSchema`. The `WORKER_CONNECTED` handshake is a NATS request/reply resolved on a private reply inbox, not a `SYSTEM` broadcast, so the `System` prefix was misleading; the wire format (subject, `action` values, payload shape) is unchanged. `inbox_schema.py` still reuses `SystemSchema` (the shared envelope), `SystemActionEnum`, and `CryptoLeverageInitSchema` from `system_schema.py`, along with the salvage helpers that only the ACK schema needs.
- **One-open-order-per-symbol guard.** A new entry (`LONG`/`SHORT`) is now **rejected** whenever any active (`OPENED`/`TP1`) position is already open on the same **symbol**, regardless of which strategy holds it — a stricter, per-symbol rule that runs ahead of the `MAX_OPEN_ORDERS` count cap. Unlike the previous behaviour, this intentionally also rejects a **same-strategy re-entry or scale-in** while an order on the symbol is live: no new order is placed until the symbol is flat. A rejected entry follows the existing reject path (`BaseSignalProcessor._reject_signal`): it is audit-logged in `position_logs`, recorded as a `REJECTED` position row and forwarded to the broker via `PositionCDC` on the `TRADE` subject with status `REJECTED` (so the broker sees the signal was received but rejected), and an `Order Rejected` operator notification is sent — no order reaches the broker. The check is applied at the single `_process_signal` funnel, so it covers both live SIGNALs and `RETRY_SIGNALS` replays, and is market-agnostic (shared by FOREX and CRYPTO) via the new `BaseSignalProcessor._symbol_open_rejection` guard backed by `PositionRepository.get_open_positions_for_flat(symbol=...)`.
- Grouped the flat `Settings` fields into nested `<specific>Settings` sub-models on the main `Settings` (`settings.nats.url`, `settings.forex.login`, `settings.telegram.enabled`, `settings.crypto.*`, `settings.strategy.*`, `settings.risk.*`, `settings.web.*`, `settings.database.file`, `settings.broker.*`, `settings.logging.*`), with `market_type`/`account_id` kept at the top level. Each group is its own `BaseSettings` reading the **same flat environment variables** as before (preserved via per-field `validation_alias`), so `.env` files and deployment are unchanged. A new `Settings.flat_dump()` reproduces the exact legacy flat `settings_dict` (original keys, `SecretStr`/enum members intact) that worker subprocesses, gateways and presenters consume via `settings_dict.get("<flat_key>")`, so that contract is untouched; `app.py` now builds the worker dict with `flat_dump()`. Direct singleton readers (`main`, `app`, `logger`, `context`, `worker_runtime`, `nats`/`notification` services, `db.connection`) were updated to the nested access. The README gains a **Settings** section documenting the groups, and a regression test pins `flat_dump()` to the legacy key set and type-preservation.
- **Breaking (ADMIN routing):** `ADMIN` `FLAT` commands now travel on **two** subjects with distinct rules. The **public** `ADMIN` subject (fanned out to every worker) no longer carries `account_id` at all — it is filtered only by the optional `market`/`gateway` dimensions. A new **private** subject `ADMIN.<market>.<gateway>.<account_id>` lets the broker address exactly one worker; every worker now subscribes to its own private subject (built from `MARKET_TYPE`, the gateway/platform setting, and the account id) in addition to the public one.
  - `AdminFlatSchema` (public) drops `account_id` and keeps `market`/`gateway` as optional filters. A new `PrivateAdminFlatSchema` requires `market`/`gateway`/`account_id` — the private subject addresses one worker, so the payload must carry the full composite identity and the worker re-validates all three against its own identity (`self._market_type` / `self._gateway_value` / `self._account_id`) before acting.
  - `BaseSignalProcessor._handle_admin_message` gains a `private` flag selecting the schema and routing rule; `_process_message` routes the public `ADMIN` subject (`private=False`) and the worker's own `_private_admin_subject` (`private=True`). `_flat_targets_this_worker(admin, *, private)` applies optional `market`/`gateway` filtering on the public path and a strict exact-match of all three fields on the private path.
  - `connect()` subscribes to `_private_admin_subject` (`ADMIN.<market>.<gateway>.<account_id>`) alongside the configured subjects; it is `None` (public-only) when the identity is incomplete.
  - README `ADMIN Subject` section documents both subjects.
- The `examples/` payload folder is renamed `examples/signals` → `examples/nats` and now enumerates **every** subject/action the worker exchanges with the broker (one runnable JSON per action), plus a new `examples/nats/subjects.md` describing each NATS subject and action from the worker's point of view (mirrors the Broker's `subjects.md`). New examples: `admin.flat.json` (private, account-scoped), `admin.flat.broadcast.json` / `admin.flat.all.json` (public), `entry.long.scale.json` (scale-in), `system.retry_signals.json`, and per-status `TRADE` events (`trade.created.{opened,rejected}.json`, `trade.updated.{tp1,tp2,sl,r_sl,terminal_closed,forced_closed,flatted}.json`).
- **Breaking (broker payload):** `account_id` alone is not a unique worker identity — the same raw id can collide across markets/gateways (e.g. an email used as `account_id` also matching a CRYPTO gateway name). The broker now sends `market` and `gateway` alongside `account_id` on the `ADMIN` `FLAT` command, and every place that previously routed by `account_id` alone now matches the full composite key `(market, gateway, account_id)`.
  - `AdminFlatSchema` gains optional `market` / `gateway` fields (mirrors `SystemWorkerConnectedSchema`). `BaseSignalProcessor._handle_admin_message` now calls a new `_flat_targets_this_worker` helper: each of `account_id` / `market` / `gateway` is an independent optional filter — present in the payload it must match this worker's identity (`self._account_id` / `self._market_type` / `self._gateway_value`), absent it does not filter that dimension. A broadcast FLAT (all three unset) still targets every worker.
  - `PositionEvent` (the `TRADE` subject payload) gains a `gateway` field, populated from `BaseSignalProcessor._gateway_value` and threaded through `PositionCDC(gateway=...)`. Its market field is renamed `market_type` → `market` to match the Broker's field name; the broker can now upsert a Trade row by the full `(market, gateway, account_id, ticket)` key instead of `account_id + ticket`.
  - `examples/signals/admin.flat.json` updated with `market` / `gateway`.
  - NATS error/disconnect callbacks now deduplicate at source — nats.py fires `error_cb`/`disconnected_cb` from multiple internal coroutines (reader, flusher, pinger) for the same connection event, producing duplicate Telegram error-log messages that the downstream `TelegramLogHandler` dedup did not reliably catch. A per-connection `_CallbackDedup` guard on both `NATSSubscriber` and `NATSPublisher` now suppresses identical callbacks within the configured `TELEGRAM_LOG_DEDUP_WINDOW` (default 60 s) before they reach the logger.
- Extracted the entry guards (`MAX_OPEN_ORDERS` cap and one-open-order-per-symbol) out of `BaseSignalProcessor` into a new `worker/gateways/guard.py` module — `guard.symbol_open_rejection(db_service, signal)` / `guard.max_open_orders_rejection(db_service, settings, signal)` are now plain functions (taking the DB service/settings/signal explicitly) rather than processor methods, called from `_process_signal` in their place. Pure code-organization change with no behavioural difference; keeps `processor.py` focused on message dispatch.
- CRYPTO: `CryptoReconcileJob` now subclasses `BasePositionReconcileJob` — behaviour, constructor signature, thread name (`crypto-reconcile`) and 45 s cadence are unchanged; only the shared loop/confirmation logic moved to the base, leaving the crypto job with its symbol-based correlation hooks.
- `scripts/init_env.py` now prompts for `FOREX_ALLOW_MULTI_STRATEGY_PER_SYMBOL` as part of the FOREX group. The group is renamed `MT5_KEYS` → `FOREX_KEYS` (and its section header `MT5 Connection Configuration` → `FOREX / MT5 Configuration`) because it no longer holds only MT5 connection credentials — the toggle is a FOREX trading-behaviour setting that belongs with them, and it is risky enough (it needs a hedging account) that it should be an explicit answer during setup rather than a default silently inherited from `.env.example`. Gating is unchanged: a `MARKET_TYPE=CRYPTO` run still skips the whole group and keeps its existing values.

### Fixed

- **FOREX: a position closed by hand in the MT5 terminal was never detected while the FOREX weekend window was open.** Both close detectors gated their scan on `is_market_closed()` (Fri 22:00 → Sun 22:00 UTC): `MT5EventJob` skipped its 5 s poll outright and `ForexReconcileJob._should_scan` returned `False` before any other check. The assumption — nothing can trade while the trade server is down for maintenance — does not hold for a broker's **24/7 instruments**: crypto CFDs such as `BTCUSD` trade straight through that window, the terminal stays connected (the health thread parks it only at its *next* check, up to 15 min in), entries still fill, and the position can still be closed manually. Both jobs slept through exactly that, so the DB row stayed `OPENED` all weekend, no `TERMINAL_CLOSED` status or Telegram notice was produced, and the row went on blocking every later entry on that symbol until an operator sent an `ADMIN FLAT`. Worse, neither skip logged anything, so the jobs looked dead. Both are now gated on the **live platform connection** — the only state that actually makes `positions_get()` meaningless (`None` → `[]` → "everything is flat") — and log a `DEBUG` line when they skip. Only the *cadence* still consults the calendar: each job backs off to `MT5_HEALTH_INTERVAL_WEEKEND` when the market is closed **and** the connection has actually been parked, and otherwise keeps its normal 5 s / 60 s cadence — including on a weekday disconnect, so polling resumes the moment the health thread reconnects. `MT5EventJob` takes an `is_connected` probe (wired from `MT5Gateway.is_connected` in `create_close_detection_job`) for this.
- **FOREX: a manual close after our own TP1 partial was silently discarded.** `close_detector._build_event` selected the **first** `DEAL_ENTRY_OUT` deal in a position's history. A position that had already been partially closed by the worker carries that partial as its first OUT deal with `DEAL_REASON_EXPERT`, which maps to no `TerminalCloseReason` — so the function returned `None` at `DEBUG` level and the *later*, genuinely terminal-initiated close (manual, SL, TP) was never even examined. It now picks the **newest** closing deal by `(time, ticket)`, and `DEAL_ENTRY_OUT_BY` (a position closed against an opposite one) counts as a closing deal alongside `DEAL_ENTRY_OUT`. Ordering of `history_deals_get` is no longer assumed.
- **FOREX: one bad terminal-close event silently discarded every remaining close in the same batch.** `MT5EventJob._run` wrapped the whole `for event in events` loop in a single `try`, so an exception raised while handling one event aborted the rest — permanently, because `scan_terminal_closed_positions` had already advanced `seen_tickets` past the entire batch and those tickets never look "disappeared" again on a later scan. Each event is now handled inside its own `try`, logging `Failed to handle terminal close | ticket=… reason=…` and continuing (a failure before the DB write still leaves the row open for `ForexReconcileJob` to reconcile). The concrete trigger was the notification builder: `TerminalClosedEvent.sl`/`tp` are read off the position's *opening order* and are `Optional` — `history_orders_get` legitimately returns nothing for it on pruned broker history or a position opened outside the worker — but the Telegram message called `round(event.sl, 2)`, which raises on `None`. Because the DB writes run first, the row was still marked `TERMINAL_CLOSED` correctly; what was lost was the operator notification for that close *and* every close queued behind it. Prices now render through a `_fmt_price` helper that shows `—` for a missing value.
- **FOREX: `MT5EventJob` held a stale snapshot of the worker's magic numbers.** The job was built with `ForexExecutor.owned_magics()` — the resolved set — but the magic map is broker-owned and re-pushed on **every** `WORKER_CONNECTED_ACK`, and a NATS reconnect re-runs the handshake. Any magic added or changed after startup was invisible to the job: `positions_get()` results were filtered against the old set, the worker's own tickets never entered `seen_tickets`, and terminal-close detection went permanently blind for those strategies with no error anywhere. It now receives the `owned_magics` **callable** and resolves it per scan (`ForexReconcileJob` was already immune, reading through the executor). An empty result — the state a dropped or omitted `strategy_magic_map` leaves the worker in — now logs one `No owned magics — terminal-close detection is INACTIVE` warning instead of no-op'ing silently, re-arming if magics later come and go again.
- **FOREX: the order-fill notification always claimed the worker had sized the lot itself.** `ForexMessagePresenter.order_filled` passed `auto_calculated=True` to `format_volume` unconditionally, so the ⚙ gear — which means "this volume was computed by the worker, not taken from the signal" — was printed even under `VOLUME_DECISION_ENABLED=false`, where the lot is `signal.quantity` verbatim. An operator reading the fill had no way to tell which sizing mode actually produced the order, and the icon contradicted the override block in the same message. The flag now follows `settings_dict["volume_decision_enabled"]` (absent settings ⇒ no gear), mirroring `_risk_line` and the `(TP1 x%)` suffix, which are already suppressed in that mode. Display-only — the executed volume is unchanged.
- Private `ADMIN` FLAT (and `BLOCK_SIGNAL`/`ALLOW_SIGNAL`) was silently dropped when the broker sent `account_id` as an integer (e.g. the MT5 login `413652379`) in the payload. Pydantic v2 does not coerce `int → str` on a plain `str` field, so `PrivateAdminSchema(**data)` raised a `string_type` `ValidationError`, which `_handle_admin_flat` logged at ERROR level but never surfaced as a close action — from the outside it looked like the worker had not received the message. `PrivateAdminSchema` now sets `model_config = ConfigDict(coerce_numbers_to_str=True)` so `account_id` normalises to `str` before `_flat_targets_this_worker` compares it to the worker's stringified `_account_id`; both `int` and `str` payloads now proceed to the close/reconcile path. Regression covered by `test_private_numeric_account_id_is_coerced_to_str`.
- A FOREX signal for a strategy missing from `STRATEGY_MAGIC_MAP` used to bubble a `KeyError` out of the executor as an unhandled "manual reconciliation may be required" error at the top of the NATS loop — alarming for the operator and giving no clue what to fix. `BaseSignalProcessor._process_signal` now probes `_magic_for(signal.strategy)` up front; on `KeyError`/`ValueError` the signal is skipped cleanly with an `ERROR` log (naming the missing strategy and pointing at `STRATEGY_MAGIC_MAP`/`NATS_SUBJECTS`) and a `signal_rejected` operator notification, before any DB row is written or the broker is contacted. CRYPTO's `_magic_for` always returns `None`, so the guard is a no-op there.
- `FLAT` no longer falls back to an **unscoped** `close_all_positions(strategy=None)` when the multi-strategy toggle is on. That retry exists to catch a position live at the broker but missing from the DB; with several strategies sharing a symbol it would flatten the *other* strategies' live positions while cleaning up this one. It is skipped (and logged) in that mode, leaving the untracked position to the terminal-close detector / reconciler. Behaviour with the toggle off is unchanged.

## [1.2.0] - 2026-07-18

### Added

- `MAX_OPEN_ORDERS` (int, default `5`; `0` in `.env.example` disables) env var — a worker-side exposure cap on how many positions may be concurrently open. When a new entry (`LONG`/`SHORT`) would push the count of active (`OPENED`/`TP1`) positions **across every strategy and symbol** past the cap, the entry is **not** sent to the broker: it is recorded in SQLite as a `REJECTED` position row, forwarded to the broker via `PositionCDC` on the `TRADE` subject with status `REJECTED` (so the rejected signal is visible end-to-end), audit-logged in `position_logs`, and an `Order Rejected` operator notification is sent — but no order is placed. A re-entry or scale-in on a symbol the strategy already holds **replaces** the existing position rather than opening a new slot, so it never counts against the cap. Exits (`TP1`/`TP2`/`SL`/`R_SL`/`FLAT`) are never gated, so a position can always be closed even at the cap. Set to `0` to disable the limit entirely. The guard is market-agnostic — the shared `BaseSignalProcessor._max_open_orders_rejection` check and `_reject_signal` handler run identically for FOREX and CRYPTO, backed by `PositionRepository.insert_rejected_position` and the `BaseMessagePresenter.order_rejected` message.
- `PositionStatusEnum.REJECTED` — a new terminal lifecycle status for a position row that a worker-side policy (currently `MAX_OPEN_ORDERS`) blocked before it reached the broker. The row is auditable and, being neither `OPENED` nor `TP1`, never occupies the one-active-position slot, so a real position can still open later on the same `(strategy, symbol)`.
- `WORKER_CONNECTED` handshake now ships the worker's **subscribed strategies** (`strategies: list[str]`) alongside `market` and `gateway` — the strategy-name subjects in `NATS_SUBJECTS` minus the control subjects (`ADMIN`/`SYSTEM`). Extracted via the new `worker.gateways.processor.parse_strategy_subjects` helper and populated on `SystemWorkerConnectedSchema`. The broker uses this list to decide which strategies' recent signals to include in a `RETRY_SIGNALS` replay for this worker, so a worker that reconnects after a brief outage can be caught up without the broker having to guess its subscription set.
- `SystemActionEnum.RETRY_SIGNALS` + `SystemRetrySignalsSchema` — new inbound SYSTEM action (either as a `WORKER_CONNECTED` reply or a live SYSTEM push) carrying a list of `SignalSchema` payloads for the strategies this worker subscribes to. Handled generically by `BaseSignalProcessor._handle_retry_signals` (both FOREX and CRYPTO get identical replay semantics): each signal is (1) deduped against `position_logs.signal_id` — a signal we've already processed (successfully or as a REJECT) is skipped — and (2) age-gated against `MAX_RETRY_TIMEOUT` (default `60`s in `worker.settings`) using the signal's own `timestamp`; older replays are dropped so the worker never fires a stale entry/exit fill hours after the market moved. Eligible signals go through the normal `_process_signal` pipeline — order placement, DB persistence, notifications — so a replayed entry is indistinguishable from a live one. A malformed envelope or a single bad signal in a batch never aborts the rest.
- `position_logs.signal_id` / `positions.signal_id` (TEXT, nullable) — new columns populated by `log_position` / `insert_position` / `insert_rejected_position` with the originating `SignalSchema.signal_id`. The RETRY_SIGNALS handler's dedup gate reads `position_logs.signal_id` via the new `PositionRepository.signal_exists(signal_id)` method (backed by an index on the column so the lookup stays O(log n) as the log grows); a DB error is fail-safe (treats the id as seen so a replay never double-executes).

## [1.1.7] - 2026-07-15

### Changed

- FOREX: the MT5 health loop is now **market-hours-aware**, so a routine weekend disconnect no longer floods the logs and Telegram. The FOREX market is closed from **Friday 22:00 UTC to Sunday 22:00 UTC** while the broker's trade server is offline for its weekly maintenance — a disconnect in that window is expected, not a crash, and reconnecting cannot succeed until the market reopens. During the closed window the health thread now **closes the MT5 connection once**, backs off from the 15s cadence to `MT5_HEALTH_INTERVAL_WEEKEND` (default 15 min), and stays idle — no reconnect attempts and no `taskkill terminal64.exe` relaunch storm — until the first check after the window, when it reconnects through the normal path. A single "Market Closed" notice is sent when the connection is closed for the weekend (and the usual "reconnecting"/"connected" pair when the market reopens), replacing the previous per-disconnect storm of Telegram messages. `MT5EventJob` (the terminal-close detector) likewise pauses its 5s polling while the market is closed, so it no longer logs a "terminal offline" warning on every scan. Open-market behaviour is unchanged — a genuine disconnect still triggers the full aggressive relaunch/reconnect path immediately. The health-loop wait is now interruptible (`stop_event.wait`) so shutdown isn't delayed by the long weekend interval. New module constants `MT5_HEALTH_INTERVAL_WEEKEND`, `MARKET_CLOSE_HOUR_UTC` and `MARKET_OPEN_HOUR_UTC` (both default `22`; drop to `21` if your broker follows northern-hemisphere DST), plus the `is_market_closed()` helper, in `worker.settings`.

### Added

- CRYPTO: `CRYPTO_HEDGE_MODE` (bool, default `true`) env var — the exchange Position Mode the worker **enforces** on the account at startup. Rather than requiring the operator to set it by hand (Binance app/web → Futures → Preferences → Position Mode), the gateway reconciles the account into this mode right after `connect()` via the new generic `BaseExchangeGateway.set_position_mode(hedge_mode)` hook (Binance: `POST /fapi/v1/positionSide/dual`). When `true` (Hedge), every order (market open/close, stop-loss, take-profit) carries an explicit `positionSide` (`LONG`/`SHORT`) and omits `reduceOnly` entirely, since Binance rejects `reduceOnly` in Hedge Mode. When `false` (One-way), orders omit `positionSide` and closing orders use `reduceOnly` instead. The switch is best-effort: Binance `-4059` ("No need to change position side.") means the account is already in the requested mode (treated as success), and a reject (e.g. `-4068` with open positions/orders) is logged and the worker proceeds on the current mode — where a mismatch then surfaces as `-4061` ("Order's position side does not match user's setting.") on the first order. `set_position_mode` is defined on the agnostic CEX contract (default no-op returning `True`), so it is reusable across exchanges and is driven generically from `CryptoSignalProcessor._connect_broker`. Threaded through `BinanceFuturesGateway.__init__(hedge_mode=…)` and `ExchangeFactory`. The worker still only ever tracks one net position per symbol regardless of this setting — it does not manage simultaneous LONG and SHORT positions on the same symbol even in Hedge Mode.
- CRYPTO: the crypto worker's `[Connected]` startup banner now includes a `POSITION MODE` line (`Hedge` / `One-way`, from `CRYPTO_HEDGE_MODE`), so operators can confirm at a glance which Position Mode the connected worker is configured for alongside `EXCHANGE` and `TESTNET`.
- CRYPTO: the periodic reconciler (`CryptoReconcileJob`) now also imports **manually-opened positions** — a position live on the exchange that no DB row tracks (opened directly via the Binance UI / app / a third party, never through a worker signal). The same live-vs-DB scan that self-heals missed closes now, in the other direction, detects an untracked live position and — once confirmed on two consecutive scans (so a worker-opened position still mid-persist is never misread as manual) — persists it as an `OPENED` row under the synthetic `MANUAL` strategy with a unique `ref_source_id`. The CDC job then publishes it as a `CREATED` TRADE event and the existing close backstops (user-data stream / missed-close reconciler) manage it like any other position. Wired via a new optional `manual_handler` on `CryptoReconcileJob` and `CryptoSignalProcessor._on_manual_position`; an operator notification (`Manual Position Imported`) is sent per import.

## [1.1.5] - 2026-06-26

### Added

- **Telegram error-log forwarding** — When `TELEGRAM_ENABLED` and `TELEGRAM_LOG_ERRORS_ENABLED` are both set, log records at `ERROR` level or above are forwarded to Telegram. `TelegramLogHandler` (a `logging.Handler`) formats each record and hands it to a bounded queue drained by a background **thread** that performs the synchronous `send_message`, so `emit` never blocks the caller (FastAPI event loop, FOREX child process, or a daemon thread) or raises. A thread is used rather than an asyncio task because the FOREX processor runs in a child process with no event loop; the handler is process-aware and (re)starts its worker per PID so a forked child forwards through its own thread. Three safeguards keep it production-safe: a filter drops records emitted by the send path itself (no feedback loop), identical messages are suppressed within `TELEGRAM_LOG_DEDUP_WINDOW` seconds (no spam), and the queue is bounded, dropping records under an error storm rather than growing unbounded.
- **Dedicated log bot/chat** — `TELEGRAM_LOG_BOT_TOKEN` and `TELEGRAM_LOG_CHAT_ID` route forwarded error logs through a bot and private chat kept separate from the main signal bot, so an outage or ban on one never affects the other. Both fall back to `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` when left empty.
- Scale-in (averaging) position support on the SIGNAL path. The webhook/NATS SIGNAL payload now carries an `is_scale_position` boolean and a nested `scaling` object (`tp`, `sl`, `quantity`). The broker pre-applies these multipliers, so `sl`/`tp1`/`tp2`/`quantity` arrive already scaled and the worker uses them verbatim for order entry, notifications, and persistence. The only re-derivation is in risk-based sizing: when `VOLUME_DECISION_ENABLED=true` the worker sizes the entry from risk/capital/SL (ignoring `signal.quantity`), so it re-applies `scaling.quantity` to that self-computed volume. `scaling.tp`/`scaling.sl` are never re-applied; non-scale signals and an absent `scaling.quantity` are no-ops.
- Entry notifications now render a "Scaled Position" block (TP1/TP2, plus SL for forex) when a signal is flagged `is_scale_position`, displaying the broker's already-scaled targets.

### Changed

- Refactored the Telegram message presenters to remove duplication. The market-agnostic messages (`signal_rejected`, `position_unprotected_closed`) and the shared divider now live in a new `BaseMessagePresenter` (`worker/gateways/message_presenter.py`) that both the forex and crypto presenters inherit (DRY). Renamed `TradeMessagePresenter` to `ForexMessagePresenter` for naming consistency with `CryptoMessagePresenter`.

### Fixed

- Binance user data stream stopped receiving events after the `listenKey` expired. On keepalive failure the stream only retried every 30s without reconnecting, so once Binance dropped the `listenKey` (~60 min after a sustained failure) no further `ORDER_TRADE_UPDATE` events arrived. Now error `-1125` (listenKey gone) triggers an immediate reconnect, and any other keepalive error reconnects after 5 consecutive failures (~2.5 min) to recover from transient 403s (IP restriction / permission changes).
- CRYPTO: TP2 resting order was never placed on entry — `open_position()` registered the stop-loss but silently skipped the take-profit even when `tp2` was present in the signal. Positions ran without a resting TP target until the next SL move.
- CRYPTO: TP2 resting order was wiped when the stop moved to breakeven — `update_position_sl()` called `cancel_all_orders()` which cleared both the old SL and the still-valid TP2. Now the original TP2 price is recovered from the persisted entry signal and re-placed immediately after the new breakeven stop.
- CRYPTO: A new entry signal could silently cancel another strategy's SL/TP orders for the same symbol — `cancel_all_orders()` is symbol-scoped, not strategy-scoped, so the stale-position cleanup in `_handle_entry()` would wipe a concurrent strategy's resting orders before the netting-conflict guard in the executor had a chance to reject the entry. The guard now runs at the top of `_handle_entry()`, before any exchange call is made.
